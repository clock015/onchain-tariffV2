# Market 机制说明

本文说明当前 `Market.sol` 的核心经济逻辑：系统如何通过交易铸造治理权，如何收取动态关税，以及如何用顺差、逆差积分鼓励参与者在市场中持续买卖。

## 1. 通过交易铸造治理权

每一笔通过 `Market.trade(...)` 完成的交易，都会产生一笔固定的 `vaultFee`：

```solidity
vaultFee = amount / 100
```

也就是交易额的 1%。这 1% 会直接转入 `vault`，同时作为治理权的发行依据：

- 买方获得 `buyerRights`；
- 卖方获得 `sellerRights`；
- 两边铸造的数量都等于本次交易的 `vaultFee`。

这意味着治理权不是预挖、购买或转让来的，而是从真实交易行为中产生。谁参与了市场，谁就在对应身份侧积累治理权。

### 买方权利和卖方权利

系统把治理权拆成两类：

- 买方权利：来自消费、采购、付款等买方行为。
- 卖方权利：来自销售、供给、收款等商家行为。

这两类权利分别进入买方治理 token 和卖方治理 token。治理时，系统不是简单统计单边票数，而是要求买方和卖方都形成支持。有效票数取两侧票数的较小值：

```text
effectiveVotes = min(buyerSideVotes, sellerSideVotes)
```

一个简单例子：

```text
买方侧：
支持 80 票，反对 20 票

卖方侧：
支持 50 票，反对 40 票
```

系统不会把两边票数直接相加成“支持 130、反对 60”，而是分别对支持票和反对票取两侧较小值：

```text
有效支持票 = min(80, 50) = 50
有效反对票 = min(20, 40) = 20
```

最终计票结果是：

```text
支持 50 票 > 反对 20 票
```

所以该提案在双边共识口径下通过。这个例子里，买方支持很多，但最终有效支持票被卖方侧的 50 票限制住；卖方反对更多，但有效反对票被买方侧的 20 票限制住。

因此，只有买方支持但卖方不支持，或者只有卖方支持但买方不支持，都不能单独主导市场规则。治理结果必须同时得到市场需求侧和供给侧的认可。

### 治理市场和准入权

`Market` 的关键管理权限最终交给治理系统执行。治理可以管理市场规则，也可以处理商家准入后的风险。

当前 `Market` 中最直接的准入治理动作是 `kickMerchant(accountId)`。只有 `governance` 地址可以调用它。账户被踢出后：

- 账户及其 owner–merchant 配对状态被清空；
- 最多按当前应税顺差数额罚没资金，并先使用押金、押金不足时再使用已扣留关税；
- 罚没资金进入 `vault`；
- 剩余押金（包括待退押金）立即退给 Account Owner；
- 剩余已扣留关税立即退给 Merchant；
- 该账户不再是 active merchant account，不能继续接单或付款。

也就是说，商家可以通过押金进入市场，但其持续经营资格仍受治理约束。治理权又来自交易贡献，所以市场准入和市场治理形成闭环：活跃参与者获得治理权，治理权再反过来维护市场秩序。

## 2. 关税、顺差与逆差积分

交易发生时，系统不会简单把固定比例全部给商家或全部留在税池。当前 `Market.sol` 使用 AMM 公式，在商家可提现现金和税池积分之间动态分配交易额。

一笔交易的总额为 `amount`。系统先固定扣除 1%：

```text
vaultFee = amount / 100
```

剩余 99% 记为 `P`：

```text
P = amount * 99 / 100
```

这 99% 会被拆成两部分：

```text
P = deltaW + deltaS
```

- `deltaW`：本次转给商家或业务合约的现金部分。
- `deltaS`：本次留存在 `Market` 税池中的关税积分部分。

交易完成后：

- 商家的累计提现量 `W` 增加 `deltaW`；
- 买方的 `buyerPoints` 增加 `deltaS`；
- 卖方的 `sellerPoints` 增加 `deltaS`；
- `Market` 合约中实际沉淀 `deltaS` 对应的资金，形成可用于退税的税池。

### 顺差和逆差如何形成

系统用两个积分账本描述用户在市场中的位置：

- `buyerPoints`：买方积分，可以理解为逆差积分。用户买入越多，资金流出越多，逆差积分越多。
- `sellerPoints`：卖方积分，可以理解为顺差积分。用户卖出越多，资金流入越多，顺差积分越多。

如果一个地址只买不卖，它会不断积累逆差积分；如果一个地址只卖不买，它会不断积累顺差积分。随着交易持续发生，市场中的顺差和逆差不会马上消失，而是分别在不同账户上不断富集。

这种设计会让市场状态留下可计算的轨迹：

- 消费者的买入行为沉淀为逆差积分；
- 商家的销售行为沉淀为顺差积分；
- 同一个参与者既买又卖时，两类积分会在其账户内形成可对冲关系。

### 退税如何鼓励积极参与市场

退税不是只奖励买方，也不是只奖励卖方。系统要求同一账户同时拥有买方积分和卖方积分，才能对冲退税。

可退税基础额度为：

```text
totalRefundable = min(buyerPoints[account], sellerPoints[account])
```

也就是说：

- 只有逆差积分，没有顺差积分，无法退税；
- 只有顺差积分，没有逆差积分，也无法退税；
- 同时有逆差和顺差，才能按较小的一侧退税。

这会鼓励参与者不是单向地消费或单向地出售，而是更积极地参与市场循环。一个商家如果也作为买方采购，或者一个买方也参与供给，就能把自身的顺差和逆差对冲掉，从税池中拿回对应部分。

退税执行后，系统会同时扣减两边积分：

```text
buyerPoints[account] -= actualClaim
sellerPoints[account] -= actualClaim
claimed[account] += actualClaim
```

因此，退税本质上是把账户内已经匹配的顺差和逆差进行结算，而不是凭空发放补贴。

## 3. 关税计算细节

当前关税模型的核心目标是：根据商家的押金、已提现现金量和市场中积累的顺差程度，动态决定新交易中有多少资金可以立即给商家，有多少资金应该继续留在税池。

每个商家有几个关键参数：

- `D`：商家押金，即 `deposit`。
- `W`：商家累计已提现现金量。
- `leverageFactor`：杠杆参数，决定商家最多可以基于押金提现多少现金。
- `virtualDepthRatio`：虚拟深度参数，用来平滑 AMM 曲线。
- `S`：商家当前顺差富集程度，由 `sellerPoints - buyerPoints` 得出；如果卖方积分不大于买方积分，则为 0。

系统先计算商家的最大可提现上限：

```text
MaxW = D * leverageFactor / 100
```

再计算虚拟深度：

```text
Y = S + D * virtualDepthRatio / 10000
```

其中 `S` 越大，表示该商家的顺差越富集；`virtualDepthRatio` 则给曲线提供基础深度，避免早期交易过度剧烈。

商家剩余可提现空间为：

```text
R = MaxW - W
```

如果 `W >= MaxW`，说明商家已经达到当前押金和杠杆参数允许的提现上限，本次 99% 交易额会全部进入 `deltaS`，不再产生新的 `deltaW`。

如果还有可提现空间，系统用如下不变量计算：

```text
(R - deltaW) * (Y + deltaS) = R * Y
deltaW + deltaS = P
```

直观理解是：

- `R` 是商家还能从系统中拿走的现金空间；
- `Y` 是商家所在税池曲线的深度；
- 当本次交易让商家获得 `deltaW`，可提现空间会减少；
- 同时税池中沉淀 `deltaS`，顺差/关税深度会增加；
- 系统通过 AMM 曲线在二者之间自动找到平衡点。

最终结果是：

- 押金越高、剩余提现空间越大，商家越容易获得较高的 `deltaW`；
- 已提现越多、越接近 `MaxW`，新增交易越倾向于沉淀为 `deltaS`；
- 顺差越富集，曲线深度越大，后续交易的分配会继续随状态变化。

所以关税不是一个静态比例，而是跟随商家状态和市场交易历史变化的动态结果。

## 4. 消灭平衡的延迟顺差

退税不再按金额配额限制。系统改为识别一笔交易实际消灭了多少互相平衡的顺差和逆差：

```text
buyerSurplusReduced = positive(oldBuyerBalance) - positive(newBuyerBalance)
sellerDeficitReduced = negative(oldSellerBalance) - negative(newSellerBalance)
resolvedSurplus = min(buyerSurplusReduced, sellerDeficitReduced)
```

`resolvedSurplus` 记入买方账户的延迟顺差。双方余额跨过零点时，上述计算会自动只取真正互相抵消的部分；没有与卖方逆差配对的普通买方顺差减少仍可正常退税。

延迟顺差按押金和时间线性释放。当前默认 `resolutionRatio = 5000`、`RESOLUTION_PERIOD = 30 days`，即每 30 天最多释放相当于押金 50% 的延迟顺差：

```text
released = deposit * resolutionRatio / 10000 * elapsed / RESOLUTION_PERIOD
currentDeferred = max(storedDeferred - released, 0)
```

曲线只对合并后的应税顺差计算一次：

```text
taxableSurplus = positive(netTradeBalance) + currentDeferred
newTax = curveTax(taxableSurplus)
```

实际退款由累计关税与新理论税的差决定，并以本次 99% 交易额为上限，因此 1% 权利费始终需要支付。第三方可以代付并正常改变买方余额、形成延迟顺差和为买方 owner 铸造权利，但只有买方账户的 Merchant 为其 Account Owner 发起交易时才能实际使用退款。

这种限制针对的是系统内顺差和逆差被集中消灭的速度，而不是所有正常消费的退税金额。押金越高，延迟顺差解除得越快；增加押金只会加快此后的释放，不会追溯改变此前已经过的时间。

## 5. 机制总结

当前市场机制可以概括为两条闭环：

第一条是治理闭环：

```text
交易 -> 1% vault fee -> 铸造买方/卖方治理权 -> 双边共识治理 -> 管理市场规则和商家准入
```

第二条是税收闭环：

```text
交易 -> 动态关税 deltaS -> 顺差/逆差积累 -> 消灭平衡形成延迟顺差 -> 随时间释放并在后续消费中退税
```

这两条闭环共同服务于同一个目标：让治理权和经济收益都来自真实市场参与，而不是来自外部投机；让只买、只卖、买卖兼具的不同参与者都在链上留下可计算的市场位置，并通过顺差/逆差对冲机制鼓励更活跃、更循环的交易行为。
